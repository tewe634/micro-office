# V1.1.14 概览（list 字段子结构定义）

## 1. 版本目标

- 补齐工作流字段字典中 `list` 类型的可用性。
- 让 `list` 字段不再只是一个空类型，而是能继续定义“列表项有哪些子字段”。
- 明确 `list` 字段是“列表项对象结构”的容器，不是普通标量字段。

## 2. 现状问题

- 当前“新建字段定义”弹窗里，选择 `字段类型 = list` 后，表单仍和普通字段一致。
- 这样只能创建一个类型叫 `list` 的字段，但无法表达：
  - 列表项长什么样
  - 列表项有哪些子字段
  - 每个子字段的 key / 名称 / 类型 / 必填 / 排序
- 结果是：
  - 前端无法正确配置 list 字段
  - 后端无法稳定校验 list 字段结构
  - 节点输入输出使用 list 字段时没有完整契约

## 3. 本版设计结论

### 3.1 list 字段必须带子字段定义

当字段类型为 `list` 时，必须额外维护：

- 列表项字段集合

例如：

- 主字段：`expense_items`
- 类型：`list`
- 列表项字段：
  - `item_name` / 文本
  - `amount` / 数字
  - `remark` / 文本

### 3.2 非 list 字段不受影响

当字段类型不是 `list` 时：

- 继续保持当前普通字段定义模型
- 不展示“列表项字段”配置区

### 3.3 list 子字段也是结构化字段

list 子字段至少要支持：

- `fieldKey`
- `name`
- `fieldType`
- `required`
- `sortOrder`
- `description`

首版建议限制：

- list 子字段先不允许再次嵌套 `list`

避免首版直接走成无限递归结构。

### 3.4 最终存储口径

本版最终固定为：

- 存储位置：`mo_workflow_template_field_definitions.meta.listSubFields`

说明：

- `meta` 是字段定义扩展容器
- `listSubFields` 是 `list` 类型字段专用结构槽位
- 不采用“`meta` 直接就是数组”的方案

## 4. In / Out

### In Scope

- 字段定义页支持 `list` 子字段管理
- 后端字段定义接口支持读写 list 子字段
- 数据库存储位置固定为 `meta.listSubFields`
- 节点输入输出在消费字段定义时能读取 list 子结构

### Out of Scope

- 不做无限层级嵌套 list
- 不做可视化拖拽 schema 设计器
- 不做历史 list 字段自动推断子结构

## 5. 依赖顺序

1. 数据库线程先明确 list 子字段如何落库。
2. 后端线程扩展字段定义接口。
3. 前端线程补齐 list 字段管理交互。
4. 测试线程验证 list 字段定义、回显、消费。

## 6. 验收口径

- 新建字段时若类型选 `list`，页面会出现“列表项字段管理”区域。
- 可以为一个 list 字段新增多个子字段。
- 保存后再次打开能正确回显子字段结构。
- 非 list 字段不出现子字段管理区域。
- 节点输入输出读取字段定义时能拿到 list 子结构。
