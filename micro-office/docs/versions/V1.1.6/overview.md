# V1.1.6 概览（门户单块模板抽离与复用）

## 1. 版本目标

- 将“门户页面模板中的单块配置”从岗位模板里抽离，形成可复用的**块模板库**。
- 让多个岗位模板可以**引用同一个块模板**，避免“消息中心”这类能力块在每个岗位模板里重复手工配置。
- 保持当前 `portal template -> sections -> blocks` 运行时主链路不推倒重来，优先做**复用抽象**，不做重型低代码平台。

## 2. 问题背景

- 当前门户模板编辑器保存的是模板自身的 `sections/items/actions`，块定义内嵌在模板里。
- 现状导致：
  - 一个能力块加到销售经理模板后，其它岗位还要重新加一遍。
  - 相同块的标题、数据键、动作配置容易在多模板之间漂移。
  - 后续调整“消息中心”这类通用块时，无法一次修改、多处复用。
- 当前代码与文档已具备“section + blocks + data.blocks”的运行时概念，但**块定义还不是独立资产**。

## 3. 本版设计结论

### 3.1 采用“双层模板”模型

- **页面模板（Portal Template）**
  - 负责页面级布局、分区、顺序、岗位/主体绑定。
- **块模板（Portal Block Template）**
  - 负责单块数据模板定义，例如：
    - 消息中心
    - 待办列表
    - 销售简报
    - 客户提醒

### 3.2 块模板复用方式

- 页面模板中的 section 不再只承载“内嵌 block 配置”，而是支持**引用块模板**。
- 同一个块模板可被多个页面模板引用。
- 页面模板侧只保留**装配信息**：
  - 放在哪个 section
  - 排序
  - 是否启用
  - 少量展示级覆盖（本版默认不开放复杂覆盖）

### 3.3 本版控制边界

- 本版不做无限制 block DSL。
- 本版不支持任意脚本、任意表达式、任意 SQL。
- 本版优先支持：
  - 块模板独立管理
  - 页面模板引用块模板
  - 运行时按引用解析为现有 `template.sections[].blocks[]`

## 4. In / Out

### In Scope

- 新增块模板管理域（管理端 + API + 数据表）。
- 门户页面模板支持引用块模板。
- 运行时预览/解析支持“引用块模板 + 旧内嵌块”双兼容。
- 以“消息中心”作为首个复用试点块。
- 补充启动词，支持前端/后端/数据库/测试线程并行执行。

### Out of Scope

- 不重做正式门户 `PortalPage` 整体渲染框架。
- 不引入通用低代码平台。
- 不做复杂块级条件表达式、脚本执行、动态 SQL。
- 不要求本版把所有存量模板一次性迁完。
- 不改变现有权限体系和门户主体类型体系。

## 5. 核心模型与接口口径

### 5.1 新增块模板资产

建议新增独立“块模板”模型，最小字段包括：

- `id`
- `code`
- `name`
- `status`：`DRAFT | ACTIVE | INACTIVE`
- `displayType`
- `dataKey`
- `label`
- `scopeType`：本版建议固定为 `PORTAL_BLOCK`
- `meta`
- `actions`

说明：

- `displayType / dataKey / label / meta / actions` 由块模板自己持有。
- 页面模板引用块时，默认继承这些定义，不在页面模板里重复存一份。

### 5.2 页面模板引用块模板

页面模板 section 下新增“块引用”关系，最小字段包括：

- `id`
- `templateId`
- `sectionId`
- `blockTemplateId`
- `sortOrder`
- `enabled`
- `overrideMeta`（本版可先保留字段，但默认不开放复杂覆盖）

本版建议决策：

1. 页面模板侧**不开放覆盖 `dataKey/displayType/actions`**。
2. 页面模板侧仅负责“装配”，不是复制块定义。
3. 若某岗位确实需要不同版本的消息中心，应新建另一个块模板，而不是在引用处做深度分叉。

### 5.3 运行时兼容策略

- 旧模板：继续支持原有内嵌 `items/actions` 解析。
- 新模板：优先读取块引用，再解析块模板定义。
- 预览接口与运行时统一输出：
  - `template.sections[].blocks[]`
  - `data.blocks`

实现原则：

- 对前端渲染层保持兼容，不要求前端预览渲染器为此重写协议。
- 后端负责把“块模板引用”解析成前端现有可消费的 block 结构。

## 6. 依赖顺序

1. 数据库先补齐块模板主表与页面模板-块引用关系表。
2. 后端提供块模板管理 API 与页面模板引用解析。
3. 前端新增块模板管理页，并改造页面模板编辑页支持“引用块模板”。
4. 测试执行块模板复用流、兼容流、回归流。

## 7. 关键风险

1. **抽象过重风险**
   - 若直接做成万能 block DSL，会把当前门户模板域推成低代码平台，复杂度失控。
   - 本版必须坚持“标准块模板库 + 引用装配”。

2. **兼容风险**
   - 当前已有模板仍是内嵌 items 结构。
   - 本版必须允许存量模板不改也能继续编辑、预览、运行。

3. **覆盖失控风险**
   - 如果页面模板引用块后还能无限覆盖 block 内部字段，会回到“复制配置”的旧路。
   - 本版默认限制引用侧覆盖能力，只开放排序/启停/section 放置。

4. **数据契约漂移风险**
   - 块模板的 `dataKey/meta/actions` 一旦变更，会影响所有引用模板。
   - 后端与测试线程必须为块模板引用关系补充影响评估与回归口径。

## 8. 验收口径

- “消息中心”块模板可被至少 2 个不同岗位模板引用。
- 调整“消息中心”块模板的标题/动作/展示元数据后，引用模板预览结果一致生效。
- 存量未迁移模板仍可编辑、预览，不白屏、不丢数据。
- 页面模板编辑器可以：
  - 从块模板库选择块
  - 将块放入指定 section
  - 调整排序
  - 启停块引用
- 运行时与预览接口仍输出前端现有可消费的 `sections[].blocks[] + data.blocks`。
