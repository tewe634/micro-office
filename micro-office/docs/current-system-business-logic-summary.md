# micro-office 当前系统业务逻辑总结

> 结论先行：**当前 `micro-office` 更像一个“组织 / 岗位 / 人员 / 外部对象 / 产品”的主数据与门户聚合系统**，上层补了一套**销售协同配置**能力。它已经**不是**早期那种完整的工作流 / 线程 / 打卡 / 任务池系统；这部分运行时能力在当前后端已被迁移下线。

---

## 1. 当前系统定位

从现有代码、迁移脚本和前端路由来看，当前系统的定位可以概括为：

1. **组织与人员底座**
   - 维护组织树
   - 维护岗位
   - 维护人员资料
   - 支持主岗 + 兼职岗位

2. **权限与可见范围控制层**
   - 菜单权限
   - 用户级菜单覆盖
   - 外部对象类型权限
   - 按组织层级的数据可见范围

3. **业务主数据层**
   - 外部对象：客户 / 供应商 / 承运商 / 银行 / 第三方支付 / 其他
   - 产品：产品线、层级、分类

4. **门户聚合展示层**
   - 人员门户
   - 外部对象门户
   - 产品门户
   - 根据岗位或销售口径生成不同视图

5. **销售协同配置层**
   - 管理销售协同模板
   - 管理规则组、场景、组织绑定
   - 为销售部门配置协同参与人规则

一句话说：

**当前系统是“主数据 + 权限 + 门户 + 销售协同配置”，不是“全量流程引擎”。**

## 2. 当前业务边界

### 2.1 仍在当前后端中的核心模块

- 认证登录 / 会话管理
- 组织管理 `/api/orgs`
- 岗位管理 `/api/positions`
- 人员管理 `/api/users`
- 外部对象管理 `/api/objects`
- 产品管理 `/api/products`
- 门户聚合 `/api/portal/*`
- 权限配置 `/api/admin/permissions*`
- 销售协同配置 `/api/admin/sales-collab/*`

### 2.2 已下线或不再属于当前后端主能力的模块

结合 `README.md` 和迁移脚本 `V20__remove_workflow_and_unused_modules.sql`、`V30__decommission_workflow_runtime.sql`，以下能力已不属于当前主系统：

- 工作流 runtime
- 工作主帖 / 线程
- 节点流转
- 评论 / 引用
- 工作台接口
- 任务池
- 打卡
- 老的模块配置 / 模板配置

也就是说，当前系统里虽然还保留了一些“工作项 / 工作流状态卡片”的**展示模型**，但这更多是**门户展示数据**，而不是仍然由一套完整流程引擎驱动的真实 runtime。

### 2.3 设计文档先行、代码尚未完全落地的方向

仓库里还有两类明显偏“未来演进”的文档：

- `docs/personal-home-meta-v1.md`
- `docs/portal-template-cross-platform-integration-guide.md`

它们表达的是：

- 主页元数据协议化
- 门户模板跨平台化
- 模板与数据契约解耦

但**当前代码实际仍是 `PortalController + PortalPage` 的页面驱动聚合模式**，还没有完全演进成统一模板运行时。

## 3. 核心业务对象与关系

当前系统可以抽象成下面这组关系：

- **Organization（组织）**
  - 树形结构
  - 决定人员归属与可见范围

- **Position（岗位）**
  - 人员的主岗 / 兼岗
  - 岗位可以附带默认角色、对象类型权限、层级信息

- **SysUser（人员）**
  - 隶属一个组织
  - 拥有一个主岗位，可有多个辅助岗位
  - 拥有一个角色
  - 登录后携带菜单权限、对象类型权限

- **ExternalObject（外部对象）**
  - 类型包括 `CUSTOMER / SUPPLIER / CARRIER / BANK / THIRD_PARTY_PAY / OTHER`
  - 可以挂负责人，也可以挂组织 / 部门
  - 客户额外有客户角色、规模、上级客户、健康度等字段

- **Product（产品）**
  - 支持父子层级
  - 支持产品线、分类编码、三级分类

- **AuthSession（会话）**
  - 登录后创建一条 session
  - JWT 只是 session 的载体，真正的有效性由服务端 session 控制

- **Portal（门户视图）**
  - 不是单独表，而是以用户 / 对象 / 产品为中心做聚合输出
  - 按角色、岗位、scope 组装展示数据

- **SalesCollab（销售协同配置）**
  - 包含模板、规则组、规则、组织绑定
  - 解决“某销售部门下，哪些协同角色应该参与”的配置问题

## 4. 登录与会话逻辑

### 4.1 登录方式

- 支持**手机号或邮箱**登录
- 登录成功后：
  1. 创建 `auth_session`
  2. 生成 JWT
  3. JWT 内写入：`sub(userId)`、`role`、`sid(sessionId)`

### 4.2 会话有效性

当前并不是纯粹依赖 JWT 的 `exp` 过期时间。

实际逻辑是：

- JWT 中带 `sid`
- 后端通过 `auth_session` 判断这个 session 是否被撤销
- 退出登录时会撤销当前 session

也就是说：

**当前系统更偏“服务端会话控制 + JWT 载体”的模式。**

### 4.3 `/users/me` 返回的含义

登录后前端会调用 `/api/users/me` 获取：

- 当前用户基础信息
- 当前菜单权限
- 当前对象类型权限
- `homePath`
- 是否有用户级自定义菜单 / 自定义对象类型

这里的 `menus` 是前端导航与页面可访问性的核心输入。

## 5. 组织、岗位、人员的业务逻辑

## 5.1 组织

组织是所有数据范围控制的根。

当前组织逻辑包括：

- 组织以树形结构维护
- `/api/orgs/chart` 会返回：
  - 组织列表
  - 组织下人员
  - 各组织人数统计
  - 人员是否可能是 leader 的辅助判断

### 5.2 岗位

岗位主要承担 4 类语义：

1. 人员身份归属
2. 角色默认来源
3. 外部对象类型权限来源
4. leader / 管理层判断依据之一

非 HR / ADMIN 用户查看岗位时，并不是全量可见，而是**只看到自己可见组织范围内、实际被人员使用到的岗位**。

### 5.3 人员

人员的关键属性是：

- `orgId`
- `primaryPositionId`
- `extraPositionIds`
- `role`
- `empNo`

### 5.4 角色来源

人员角色并不一定手工指定。

当前规则是：

1. 如果创建 / 更新时显式传了 `role`，以显式值为准
2. 否则优先取主岗位的 `default_role`
3. 主岗位没有合适角色时，再看组织的 `default_role`
4. 兜底为 `STAFF`

### 5.5 多岗位逻辑

当前系统支持：

- 1 个主岗位
- 多个辅助岗位

多岗位目前主要影响：

1. **门户展示上下文**
   - 人员门户可基于不同岗位切换展示视角
2. **外部对象类型权限并集**
   - 若没有用户级覆盖，则对象类型权限来自主岗 + 辅岗并集

但多岗位**不会自动扩大组织数据范围**。数据范围仍主要看用户自己的 `orgId`。

### 5.6 人员列表的特殊业务规则

当前人员列表不是简单的“按组织查人”。它还带一些业务增强：

- 如果查的是根组织，则只取直属人员
- 如果查的是非根组织，则递归查本组织及所有子组织
- 在部分组织场景下，还会**额外挂载固定负责人**进入结果集

也就是说：

**当前人员列表带有明显的“业务管理视角”规则，不是纯粹的主数据查询。**

## 6. 权限模型与数据范围逻辑

## 6.1 菜单权限

当前菜单权限分两层：

1. **角色菜单权限** `role_menu_permission`
2. **用户级菜单覆盖** `user_menu_permission`

优先级：

- 如果用户有自己的菜单配置，用用户级配置
- 否则回退到角色菜单配置

特别说明：

- `/org` 被视为基础菜单，逻辑上默认可见
- 前端侧边栏主要由 `menus` 渲染

## 6.2 Spring Security 粗粒度控制

后端安全规则大体上是：

- `/api/auth/login`、`/register` 公开
- `/api/users/me`、`/api/portal/**` 需要登录
- `/api/orgs` 的 GET 需要登录；修改组织需要 `HR / ADMIN`
- `/api/users`、`/api/positions` 的 GET 需要登录；修改需要 `HR / ADMIN`
- `/api/admin/**` 仅 `ADMIN`
- `/api/objects/**` 需要登录，具体可见范围交给业务层判断
- 其余接口默认登录即可

因此，当前系统是：

**Spring Security 做粗粒度，业务 Service / Controller 再补细粒度。**

## 6.3 组织数据范围

数据范围核心来自 `DataScopeService`：

- 全局管理员：可见全部组织
- 普通用户：默认看自己组织范围
- 如果用户所在组织是根组织：看根组织及其直属子组织
- 如果是普通节点：看当前组织及其全部子孙组织

## 6.4 leader 判断

系统会根据以下条件判断一个人是不是 leader 候选：

- 岗位层级较高（如 `level <= 3`）
- 岗位名称 / 编码包含“负责人、总监、经理、主管、主任、部长、组长”等关键词
- 或角色本身是管理员

这个判断会影响：

- 销售 scope 解析
- 外部对象访问范围
- 组织图中的 `leaderCandidate` 标记

## 6.5 销售 scope 逻辑

当前销售口径支持：

- `personal`
- `department`
- `business`
- `system`

但不是所有人都能切到更高范围：

- 普通人默认至少有 `personal`
- leader 候选才可能拥有 `department / business / system`
- `system` 一般要求处于销售体系根节点或全局管理员

这套规则主要服务于**销售门户 / 产品门户**的聚合展示。

## 6.6 外部对象访问逻辑

访问外部对象时，需要同时满足两件事：

1. **对象类型有权限**
   - 类型可来源于用户级配置
   - 或岗位配置并集

2. **对象本身在可见范围内**
   - 自己负责的对象可直接看
   - leader 可看自己组织范围内人员负责的对象
   - 无负责人对象则按对象挂的组织 / 部门判断

所以外部对象权限是：

**对象类型权限 × 组织可见范围 × owner 归属判断**。

## 7. 外部对象业务逻辑

## 7.1 对象类型

当前外部对象类型为：

- 客户 `CUSTOMER`
- 供应商 `SUPPLIER`
- 承运商 `CARRIER`
- 银行 `BANK`
- 第三方支付 `THIRD_PARTY_PAY`
- 其他 `OTHER`

## 7.2 数据归属方式

外部对象支持两种主要归属：

1. **挂负责人** `ownerId`
2. **挂组织 / 部门** `orgId / deptId`

如果没有负责人，则至少要有组织或部门归属。

## 7.3 客户特有字段

只有 `CUSTOMER` 会保留这些字段：

- `customerRole`
- `customerScale`
- `parentObjectId`
- `customerHealth`

非客户类型在保存时会自动清空这些客户专用字段。

## 7.4 客户层级关系

客户支持上下级关系，但系统会校验：

- 上级必须也是客户
- 不能引用自己
- 不能形成循环父子关系

## 7.5 外部对象组织归一化

系统并不是允许对象挂到任意组织节点上。

当前会把对象归属归一到一组“允许的业务根组织”，例如：

- 管理体系
- 业务一部 / 二部 / 三部
- 产品支持体系

也就是说，外部对象归属并不是完全自由树，而是有明显业务边界。

## 7.6 列表与分页

对象列表支持按以下条件筛选：

- 类型
- 组织
- 部门
- 名称
- 客户角色
- 客户规模

但最终返回结果还会再经过访问控制过滤，所以前端查出来的不是“数据库命中的全量”，而是“**命中后再过滤的可见结果**”。

---

## 8. 产品业务逻辑

## 8.1 产品主数据

产品目前是比较标准的主数据维护：

- 名称
- 编码
- 父产品
- 规格
- 价格
- 产品线
- 分类编码
- 一级 / 二级 / 三级分类

## 8.2 默认值规则

产品创建或更新时：

- 如果没传 `productLine`
- 默认补成 `ABB`

## 8.3 删除规则

如果某产品下面还有子产品，则不允许删除。

所以产品本质上是一棵可维护的产品树。

## 8.4 当前产品能力边界

产品模块当前更偏：

- 主数据维护
- 门户展示承接

还没有看到独立的交易、库存、交付、报价主流程模块在当前后端中成体系存在。

---

## 9. 门户业务逻辑

门户是当前系统最有“业务展示感”的部分，但要注意：

**门户不是在回放一套真实 workflow runtime，而是在做聚合展示。**

## 9.1 人员门户

接口：`GET /api/portal/users/{id}`

特点：

- 支持 `positionId` 作为岗位上下文切换参数
- 会返回：
  - `portalOptions`
  - `activePortal`
  - `header`
  - 若干 summary cards / 明细列表

### 人员门户的两大类视图

1. **销售人员视图** `USER_SALES`
   - 当前绩效
   - 相关客户
   - 相关产品
   - 销售排行
   - 工作状态卡片

2. **工作岗位视图** `USER_WORK_*`
   - 关联工作
   - 待办 / 进行中 / 已完成
   - 工作分桶 / 工作项

### 岗位切换逻辑

岗位切换时，系统会按岗位推导 `effectiveRole`：

- 优先岗位默认角色
- 再按岗位 code / name 兜底识别（比如销售 / 商务）
- 再回退到用户已有角色

所以人员门户的重点不是“用户静态角色”，而是：

**“当前以哪个岗位上下文来看这个人”**。

## 9.2 外部对象门户

接口：`GET /api/portal/objects/{id}`

逻辑上分两类：

1. **客户门户** `OBJECT_CUSTOMER`
   - 更强调销售绩效、相关人员、相关产品、工作项

2. **普通对象门户** `OBJECT_WORK`
   - 更强调一般工作协同信息

当前对象门户会优先基于负责人 / 相关岗位找展示视角，实在没有合适上下文时才回退。

## 9.3 产品门户

接口：`GET /api/portal/products/{id}`

特点：

- 支持 `scope` 切换
- scope 受销售层级与 leader 身份控制
- 会输出：
  - 产品汇总卡片
  - 销售汇总
  - 客户覆盖
  - 分业务部 / 分部门 / 分销售人员层级视图
  - 相关工作项

从产品门户代码可以看出，它承载的是**销售管理驾驶舱**的语义，而不是单纯产品详情页。

## 9.4 门户数据的真实性边界

这是当前系统里很重要的一点：

门户中的很多数据并不是从真实交易流水直接聚合出来的，而是通过：

- `stableSeed(...)`
- `money(...)`
- `mockDate(...)`
- 一组 ref / work item 生成逻辑

来构造出**稳定、可展示、可复现的演示型聚合数据**。

所以当前门户更适合被理解为：

- 原型级驾驶舱
- 演示型聚合页
- 门户结构与交互验证层

而不是严格的财务 / 订单 / 流程事实系统。

## 10. 销售协同配置的业务逻辑

接口前缀：`/api/admin/sales-collab/*`

这个模块当前已经相对独立，核心是：

### 10.1 管什么

1. 协同模板
2. 模板规则
3. 组织绑定
4. 协同分组与场景元数据

### 10.2 规则是怎么表达的

规则大体围绕这些维度：

- **参与角色**：主责 / 协同
- **来源类型**：
  - 指定人员
  - 岗位
  - 领导
- **解析范围**：
  - 当前销售部门
  - 当前销售大区
  - 固定组织

### 10.3 业务语义

它解决的问题是：

> 某个销售部门在某类协同场景下，应该自动带出哪些协同参与人？

例如：

- 技术协同
- 售前技术
- 售后技术
- 管理同步

系统还做了一层组归一化：技术相关组会被合并为统一的“技术协同”口径。

### 10.4 模板与组织的关系

当前支持：

- 先定义模板
- 再把模板绑定到具体组织
- 组织级还可以覆盖模板规则

因此它本质上是：

**“销售组织维度的协同规则配置系统”**。

### 10.5 当前边界

需要注意：

- 当前公开出来的是**配置管理接口**
- 还没有看到对外单独暴露的“运行时协同解析接口”

也就是说，现在更像是把配置后台先做起来了，运行时落地还没有完全独立成一个公共能力层。

## 11. 当前前端实际导航结构

从 `App.tsx` 和 `MainLayout.tsx` 看，当前前端真正落地的主导航是：

- 组织架构 `/org`
- 人员管理 `/users`
- 外部对象 `/objects`
- 产品服务 `/products`
- 系统管理
  - 权限配置 `/admin/permissions`
  - 协同配置 `/admin/sales-collab`

门户页是明细跳转页，不是左侧一级导航。

当前前端首页根路由会直接跳到：

- `/org`

这意味着虽然 `/users/me` 里会返回 `homePath`，但**当前前端首页入口仍是固定 `/org`**，并没有完全按后端 `homePath` 做个性化首页。

## 12. 当前系统里值得特别注意的“真实现状”

下面这些点非常值得在后续需求评审时反复确认。

### 12.1 这是“主数据 + 门户”系统，不是完整流程引擎

不要再默认把它理解成：

- 线程驱动
- 节点驱动
- 审批流驱动
- 工作台 runtime 驱动

这套东西在当前后端已基本退场。

### 12.2 门户展示数据带有明显的原型 / 演示性质

门户里很多金额、时间、工作项是稳定生成的数据，不是从业务流水实时汇总出来的。

### 12.3 多岗位现在更像“视图切换 + 权限并集”，不是“完整多身份运行时”

多岗位目前主要用于：

- 门户岗位上下文切换
- 对象类型权限并集

但它并没有把用户真正扩展成多套独立组织数据域。

### 12.4 人员列表存在硬编码管理规则

当前按组织查人时，不完全是标准树查询，而是带了固定负责人补充逻辑。这是很强的业务定制点。

### 12.5 前端 API 里仍有历史残留

`frontend/src/api/index.ts` 里仍保留了：

- `threadApi`
- `nodeApi`
- `commentApi`
- `workbenchApi`
- `clockApi`
- `dashboardApi`
- 老的 `templateApi` / `admin modules/templates`

但当前后端 Controller 已不再提供对应主能力。

所以后续讨论接口时应遵循：

**以当前 Controller + migration 为准，不以历史前端封装名义为准。**

### 12.6 文档与代码有少量错位

例如：

- `README` 里的模块统计数量偏旧
- 部分“未来协议文档”已经先于代码存在
- 前端仍保留部分历史 API 包装

所以现在更适合采用：

1. Controller
2. Service
3. Migration
4. 当前页面路由

作为判断“当前系统真实边界”的第一依据。

## 13. 最终归纳

如果要把当前系统的业务逻辑压缩成一段话，可以写成：

> `micro-office` 当前是一个围绕组织、岗位、人员、外部对象和产品构建的企业内部主数据与门户系统。系统通过角色菜单权限、用户级权限覆盖、对象类型权限和组织数据范围控制访问边界；通过用户门户、对象门户和产品门户对这些主数据进行聚合展示；并额外提供一套销售协同模板与组织绑定配置能力，用于支撑销售部门的协同参与规则。旧的工作流、线程、任务池、打卡等 runtime 能力已从当前后端主体中下线，门户中的“工作项”和“绩效汇总”更多承担展示与原型验证职责，而非完整业务流水的事实来源。
