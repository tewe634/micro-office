# V1.1.12 概览（新增前置弹窗参数动作）

## 1. 版本目标

- 在门户 / 日常条目动作体系中新增一种“前置弹窗参数收集”动作能力。
- 支持用户点击条目后，先弹窗输入参数，再执行后续动作。
- 本版首个使用场景是“群聊主题输入后创建群聊并跳转”，但能力本身不绑定“工作汇报会议”。
- 让模板设计阶段可以自由决定哪个条目 / 哪个 block 动作使用该能力。

## 2. 基线理解

- 当前门户动作以“直接执行”为主，例如：
  - 直接打开工作台会话
  - 直接切换主体
- 现有动作模型没有“先收集参数，再执行动作”的通用能力。
- 用户现在提出的“输入群聊主题再创建群聊”只是一个动作使用场景，不应被实现成单个条目的硬编码分支。
- 本次需求不是改 block 模型本身，而是扩展动作能力模型。

## 3. 本版设计结论

### 3.1 新增通用动作能力，而不是单条目特判

本版新增的是：

- 一个可配置的“前置弹窗参数动作”

动作执行链路：

1. 用户点击条目或卡片动作
2. 前端根据动作配置识别：该动作需要前置弹窗
3. 弹窗收集参数
4. 用户确认后，把参数提交给后端
5. 后端执行实际动作
6. 前端根据返回结果跳转或刷新

### 3.2 首个落地场景：群聊主题输入后创建群聊

本版首个使用场景是：

- 弹窗输入 `session_title` / `group_topic`
- 后端根据该参数创建群聊
- 返回新会话
- 前端进入新群

但口径必须明确：

- 这不是“工作汇报会议专属接口”
- 而是“动作支持前置输入参数”的通用能力

### 3.3 模板设计负责“选用哪个动作”

模板设计时由配置决定：

- 哪个条目使用普通直接动作
- 哪个条目使用“前置弹窗参数动作”

也就是说：

- 不是后端看到某个条目名就强行弹窗
- 不是前端看到“工作汇报会议”四个字就写死分支
- 而是动作配置本身声明需要前置表单

### 3.4 动作模型建议

建议新增一种动作能力，或给现有动作增加结构化前置配置，例如：

- `actionType = open_workbench_session`
- `preActionModal`
- `preActionFields`

或

- `actionType = create_workbench_session_with_form`

本版不强行限定最终命名，但要求：

- 配置可表达“先弹窗”
- 配置可表达“收集哪些参数”
- 配置可表达“参数提交给哪个动作”

### 3.5 参数模型建议

本版至少支持一类参数：

- 文本输入

首个标准字段可落为：

- `session_title`

最小属性建议：

- `fieldKey`
- `label`
- `inputType`
- `required`
- `placeholder`
- `maxLength`

### 3.6 后端职责

后端负责：

- 接收动作执行请求和前置参数
- 校验参数
- 执行真正业务动作
- 返回统一结果

后端不应：

- 靠条目名称硬编码识别是否弹窗
- 把输入参数仅停留在前端，不进入主链路

## 4. In / Out

### In Scope

- 动作模型支持“前置弹窗参数收集”
- 前端支持按动作配置弹窗
- 后端支持按参数执行后续动作
- 首个场景支持“输入群聊主题后创建群聊并进入”

### Out of Scope

- 不重做整个 block 模型
- 不重做整个模板 schema 的其他部分
- 不要求本版支持复杂多步表单
- 不把所有现有动作都改成前置弹窗动作

## 5. 首个场景口径

以“输入群聊主题创建群聊”为例：

1. 模板里某个条目引用了带前置弹窗的动作
2. 用户点击后看到弹窗
3. 弹窗要求输入群聊主题
4. 用户确认后，后端用该主题创建新群
5. 返回 `sessionId`
6. 前端跳转进群聊

## 6. 接口与返回口径

建议后端提供统一执行能力，至少返回：

- `sessionId`
- `sessionTitle`
- `sessionType`
- `actionResultType`

如果执行结果不是会话跳转，也应预留统一结果结构。

## 7. 依赖顺序

1. 后端先明确动作配置承载方式和执行接口。
2. 数据库确认动作配置是否需要补结构化字段或新表。
3. 前端按动作配置实现弹窗与提交流程。
4. 测试验证通用动作能力和首个群聊创建场景。

## 8. 关键风险

1. **做成条目名硬编码**
   - 会把通用能力错误做成“工作汇报会议特例”。

2. **前置参数只在前端存在**
   - 会导致后端动作真实输入不完整。

3. **动作配置不结构化**
   - 如果把弹窗字段塞进零散 JSON，后续很快失控。

4. **把能力绑死在日常**
   - 该能力应可供其他 block / 条目动作复用。

## 9. 验收口径

- 系统支持配置一种“点击后先弹窗收集参数”的动作能力。
- 模板设计阶段可以决定是否使用该动作。
- 首个场景可以完成“输入群聊主题 -> 创建群聊 -> 跳转”。
- 前后端不依赖“工作汇报会议”名称硬编码。
